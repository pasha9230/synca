Состояние на 2026-11-23 (вечер). Документ публичный, как и весь репозиторий: здесь нет ссылок на рабочие таблицы, имён, телефонов, почт и секретов. Правила работы — в `CLAUDE.md`.

## 1. Проект и цель

Tires Sync — система небольшого магазина шин. Она:
- берёт выгрузку поставщика (WebMIM), считает цены, собирает фиды Авито для нескольких аккаунтов;
- ведёт чаты Авито, обращения, CRM и заказы клиентов;
- ведёт работу трёх точек выдачи: «Рабочее место» точки (приезд, выдача, ОТХ, возвраты поставщику);
- ведёт невыкупы (ОТХ) и возвраты поставщику по акту МХ-3;
- пишет заказы в Google-таблицу через веб-приложение Apps Script.

Цель — автоматизировать путь «обращение → заказ → поставка на точку → выдача или невыкуп → продажа с ОТХ или возврат поставщику», чтобы ничего не терялось и каждая продажа была записана за тем, кто её сделал.

## 2. Стек и структура

- Python 3.10+, sqlite, панель на Flask, запуск по расписанию — таймеры systemd (`deploy/*.timer`).
- `src/tires_sync/` — весь код. Карта модулей — в `CLAUDE.md`, «Карта кода». Ключевые места последних задач:
  - `orders.py` — заказы, этапы, журнал (`add_event`), правило «один открытый заказ на телефон» (`open_order_conflict`);
  - `order_chain.py` — цепочка заказов одного клиента (таблица `order_chain`);
  - `order_oth.py`, `oth_sale.py`, `oth_swap.py`, `oth_storage.py`, `oth_point_sale.py`, `oth_point_return.py`, `oth_return_act.py` — ОТХ, продажа с ОТХ, согласование и возврат поставщику, акты МХ-3;
  - `order_reserve.py` — резерв на точке, напоминание клиенту, разбор ответа («Забрал / Продлить / Отказ»);
  - `order_sheet.py` — Google-таблица заказов;
  - `panel/` — маршруты (`routes_*.py`) и шаблоны (`templates/`, новый вид — `templates/office2/` и `templates/point2/`); права — `panel/common.py` (`SECTION_OF`, `POINT_PAGES`); база и схема — `store.py` (`SCHEMA`, `CREATE TABLE IF NOT EXISTS`).
- `tests/` — pytest; полный прогон на GitHub (проверка `pytest`, 4 части).
- `deploy/` — сервер: systemd, nginx, автовыкладка; `agent/` — агент фото на Rust.

## 5. Ключевые решения и почему

- Заказы одного клиента связываются в цепочку, а не объединяются: каждый заказ — свои шины, этап и деньги, но видно историю клиента.
- Защита «один открытый заказ на телефон» остаётся для обычного создания (защита от двойного нажатия и двух вкладок); явные кнопки «Новый заказ этому клиенту» и «Добавить заказ» создают второй заказ осознанно; повтор за минуту возвращает тот же заказ.
- Ответственный каждого заказа — тот, кто по факту с ним работал (создал или продал с ОТХ), независимо от аккаунта Авито и канала.
- Продажа точкой не меняет ответственного: бонусы и аналитика точек — отдельные задачи.
- Раздел «На ОТХ» офиса делит заказы так же, как «Рабочее место» точки, чтобы обе стороны видели одно и то же.
- Решения владельца записываются в код (docstring с датой) и тесты; новые документы в `docs/` этого открытого репозитория не кладутся.
- Запись заказа в Google-таблицу обязательна: частые повторы и явная тревога с задачей, а не тихие повторы раз в час.
- Отметка офисом «Вернули поставщику» пишется в журнал отдельной записью («Офис отметил…»), чтобы её не путали с подписью точки.

## 7. Уроки и подводные камни

- Тестового сервера нет: `master` = боевой сервер. Вливать по одному PR и только после окончания выкладки предыдущего (проверка `deploy` в Actions для коммита).
- Перед PR прогонять все файлы тестов, где встречается затронутый маршрут или модуль: `rg -l "<маршрут>" tests`. Однажды CI упал на трёх файлах, которые не прогнали локально.
- Владелец репозитория вливает свои PR параллельно. Перед вливанием: `git merge origin/master` в ветку, свежий зелёный CI; при конфликте с его PR — строить поверх его изменений, а не спорить с ними.
- Тесты ОТХ пишутся с `OTH_SPLIT = True` (как на сервере: ОТХ разбит на записи хранения), иначе тест проверяет не то поведение.
- В облачной сессии Claude GraphQL GitHub закрыт: `gh pr merge` / `gh pr view` не работают, работать через REST (`gh api repos/<владелец>/<репо>/pulls/N/merge -X PUT -f merge_method=merge -f sha=<коммит>`).
- Новая удалённая ветка в облачной сессии видна только после `git config --add remote.origin.fetch +refs/heads/<ветка>:refs/remotes/origin/<ветка>` и `git fetch`; до этого хук может ложно писать «не запушено».
- Время в фоновых задачах брать свежим (`moscow_now()` в момент вызова), а не переданным сверху — иначе решения по таймерам (повторы, тревоги) опаздывают.
- Повторы во внешние сервисы — небольшими порциями за запуск (как `MINUTE_BATCH` в `order_sheet.py`), чтобы минутный таймер не зависал.
