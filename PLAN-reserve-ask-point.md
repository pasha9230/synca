# План: спросить точку до клиента (reserve-ask-point), 2026-10-26

Уровень: RED (сообщения клиенту). Решения владельца 2026-10-26, три правки.

## 1. Резерв: сначала точка, потом клиент

Было: в последний день резерва, в рабочие часы, `order_reserve.check` сам пишет клиенту «срок резерва истекает».

Стало:
- Последний день, первый тик в рабочие часы (по умолчанию с 10:00): вместо клиента бот пишет ТОЧКЕ в ВК (тем же ключом сообщества,
  что и ответы бота, `vk_send.sender_for`): «Заказ №<WebMIM> (<клиент>, <размер>) ещё на точке? Ответьте «выдал <номер>» или
  «на точке <номер>».» Строка начинается с «Заказ №», поэтому ответ на неё в ВК даёт номер сам (`line_number`).
- Состояние вопроса — `app_state` `reserve_ask:<заказ>:<приход на точку>`: `asked|время` → `answered|…` / `silent|…` / `failed|…` /
  `unasked|…`. Переход только одним UPDATE по старому значению: из двух одновременных (ответ точки и вечерний тик) выигрывает один.
- Точка «выдал/забрали <номер>» (или ответ на вопрос) → обычная команда, заказ → «Выполнено», клиенту ничего.
- Точка «на точке <номер>» (новая команда; только если о заказе спросили в этот приход на точку, в тот же день, до конца рабочих
  часов, заказ всё ещё «Товар на точке») → клиенту «срок резерва истекает» через прежний `tell_client` (его метка и токен: один раз).
  Если резерв уже продлили (дата не та, о которой спрашивали) — клиенту не пишем.
- Нет ответа до конца рабочих часов того дня (тик в 20:00 и позже или на следующий день) → клиенту НЕ пишем, жёлтая запись
  ответственному: «точка не ответила, клиенту не отправлено».
- Спросить нельзя (у точки не ВК / ВК не привязан / нет ключа сообщества / ВК отказал) → клиенту не пишем, жёлтая запись с причиной,
  один раз за приход.
- «Можно забирать» ушло сегодня → как сейчас: точку не спрашиваем, серая запись.
- Оповещения менеджеру/владельцу накануне и в день — без изменений.
- «на точке» без вопроса, на другом этапе, после срока → ответ точке, клиенту ничего.

## 2. «выдал/забрали» без номера и не ответом

Было: «спорно: нет номера заказа» → «Входящие».
Стало (строка во «Входящих» остаётся, как сейчас, — ничего не теряется):
- у точки ровно один заказ на этапах, где «выдал» разрешён (`ISSUE_FROM`) → «Это заказ №… (размер)? Ответьте «да» или «нет».»;
  `app_state vk_issue_ask_<отправитель>` = заказ, его приход на этап, время. «да» в течение 30 мин, заказ на том же этапе с того же
  момента → выдача (как «выдал»), строка «Входящих» закрывается. «нет» → ничего не меняется. Позже 30 мин / заказ сдвинулся →
  ничего не меняется, точку просят написать номер.
- несколько → «№… — размер, №… — размер; напишите «выдал <номер>»».
- ни одного → как сейчас.
«да»/«нет» принимаются только ровно этим словом и только пока есть свежий вопрос этой точке; иначе — как обычное сообщение.

## 3. Текст клиенту без предоплаты

`RESERVE_SAMPLE` = «Добрый день. Срок хранения вашего заказа №{webmim_number} истекает {hold_until}. Если вы уже забрали заказ —
спасибо, не обращайте внимания. Если нужно продлить ожидание, напишите нам.» Имя и адресат образца прежние.
Шаблон в базе с прежним текстом владельца (слово в слово) считается старым образцом: отправляется новый текст, кнопка «Добавить
образцы» заменяет его. Изменённый владельцем текст не трогаем.

## Риски неверного сообщения клиенту и защита
- Клиенту без «на точке» точки: путь отправки только из ответа точки; `check` клиенту больше не пишет (тест).
- Дубль: метка `[резерв:клиенту:<приход>]` и токен отправки прежние; повтор «на точке» — «уже отмечено».
- Ложное «да»: только ровно «да», только свежий (30 мин) вопрос этой точке, заказ на том же этапе с того же момента; повтор события
  ВК не выполняет дважды (журнал команд).
- Гонка ответа и вечернего тика: один UPDATE по старому значению.
- Минус: точки без ВК больше не получают автонапоминание клиенту — менеджер видит жёлтую запись.
