# Автовыкладка из GitHub (включена 2026-10-19)

Решения владельца 2026-10-19: Mac-сессии больше не используются; Claude сам вливает в `master`; всё, включая RED, выкладывается на сервер само, без подтверждения. Ворота стоят до слияния: полный прогон, независимое ревью, для фидов `feed-reviewer` (CLAUDE.md).

**С переходом на публичный репозиторий (2026-10-25):** в `deploy.yml` осталась только задача `tests` (проверка `tests / pytest`), задачи выкладки на раннере сервера и `rollback.yml` нет. Выкладывает только опрос `tires-pull` (раздел «Выкладка опросом» ниже), тесты идут на `ubuntu-latest`. Откат: `ssh tires-server sudo /usr/local/sbin/tires-deploy rollback`. Описание раннера ниже оставлено как история и для его снятия.

## Как работает
1. Claude вливает изменения в `master` (`--ff-only`) по правилам CLAUDE.md.
2. GitHub Actions (`.github/workflows/deploy.yml`) прогоняет тесты. Красные тесты: дальше ничего не идёт.
3. Раннер `tires-prod` на самом сервере вызывает `/usr/local/sbin/tires-deploy deploy <коммит>` (копия `deploy/tires-deploy.sh`, работает от root). Порядок тот же, что в CLAUDE.md:
   - выкладывается только **последний** коммит `master`, код берётся из своей копии репозитория `/opt/tires-sync/repo` (не из папки раннера). Старый коммит выложить нельзя, назад только кнопкой отката;
   - в журнал пишется, затронуты ли RED-файлы (всё вне `deploy/safe-paths.txt`), чтобы в отчёте было видно, что менялись фиды, Id, база, деньги или сообщения клиентам. Выкладку это не останавливает;
   - ждёт, если идёт `tires-cycle`, `tires-orders`, `tires-stock` (проверка остатков между циклами, :10/:25/:55) или задача зеркала, либо до цикла или до прохода остатков меньше 5 минут (не дольше 75 минут, потом отказ; таймера прохода нет — он не помеха). Пока идёт цикл, таймер не показывает время следующего: это тоже ожидание. Если ничего не идёт, а время следующего цикла неизвестно 5 минут подряд, отказ «не удалось узнать время следующего цикла»;
   - копия базы `sqlite3 .backup` от `tires` (`runuser`: в режиме WAL файлы `state.db-wal`/`-shm` не должны появиться от root) → `/var/lib/tires-sync/pre-deploy-<коммит>-<дата>.db`, 3 попытки, `integrity_check`, владелец `tires:tires`. Нет копии: стоп. Старые копии удаляются, только если их больше 10 **и** им больше 14 дней;
   - код кладётся в новый выпуск `/opt/tires-sync/releases/<дата>-<коммит>/`, а `app/src` и `app/docs` становятся ссылками и переключаются мгновенно: `tires-chats` (каждую минуту) не увидит смесь старых и новых файлов. Первый запуск сам переносит нынешний код в выпуск;
   - рестарт `tires-panel`, проверка: служба `active`, `/login` и `/` дают 200/302, в журнале панели нет `Traceback`/`[ERROR]`/падений воркера. Не прошла: **сам переключает обратно** и падает красным;
   - таймеры (решение владельца 2026-10-20): `deploy/*.timer` выложенного коммита ставятся вместо установленных на сервере, если отличаются. Новые таймеры не ставятся и не включаются, выключенный не включается, не запущенный не запускается, разовые `tires-mirror-*` не трогаются. В файле таймера допустимы только печатные ASCII-знаки и строки расписания (`OnCalendar`, `Persistent`, `RandomizedDelaySec`, `AccuracySec`, `Description`, `WantedBy=timers.target`), без обратной косой: таймер из репозитория не может запустить чужую службу. Таймеры ставятся после `feed-check`; если по новому расписанию срок уже прошёл, цикл запускается сразу (`Persistent=true`). Расписание проверяется `systemd-analyze calendar`; таймер не запустился: возвращается прежний (копия в `/opt/tires-sync/deploy-state/timers/`), задача красная (код 5). В журнале «было → стало». Откат кнопкой возвращает и таймеры прежнего выпуска. `tires-deploy timers`: то же без выкладки кода;
   - `feed-check --published` и по черновику. Нашёл ошибки: код не откатывает, задача красная, решение за владельцем.
4. Публикацию делает только таймер `tires-cycle`, и его проверка перед публикацией остановит фид с ошибками. Скрипт не запускает цикл, не пишет в Авито, базу только копирует. Черновик новым кодом до цикла отдельно не собирается: `run-cycle` пишет в базу и шлёт тревоги, двойной прогон их задвоил бы.

**Откат:** `ssh tires-server sudo /usr/local/sbin/tires-deploy rollback` (кнопки Actions → rollback больше нет). Переключает код на выпуск, который был до последней выкладки. База не трогается. Второй откат подряд не делается (чтобы не прыгать обратно на плохой код). Откат отказывает, если между выпусками менялся `store.py` (там схема базы и её открытие): тогда нужен человек — `git revert` и обычная выкладка, а если менялась схема, ещё восстановление базы по `deploy/README.md` («Восстановление базы из копии»). После отката в `master` плохой коммит остаётся: Claude делает `git revert`, иначе следующая выкладка вернёт его. Если в этот момент выкладка ждёт окончания цикла, откат подождёт её 10 минут и упадёт с «идёт другая выкладка»: повторить позже.

Сами себя **не** выкладывают: systemd-службы (`.service`) и новые таймеры, nginx, `tires-deploy.sh`, `tires-pull.sh`, `sudoers`, новые зависимости в `/opt/tires-sync/venv`. Их ставит владелец вручную, до выкладки кода, который их требует.
Так ставятся и копия базы вне сервера (`tires-backup-offsite.*`) и тревога панели (`OnFailure` у `tires-panel`): шаги в `docs/backup-offsite.md`, там же внешний сторож (`.github/workflows/watch.yml`).

**Что может раннер.** Workflow с любой ветки может попасть на раннер сервера. Сервер ограничивает его так: без файла `/etc/tires-deploy/enabled` раннер не выкладывает и не откатывает; выложить можно только последний master (а в master без зелёных тестов не попасть, см. защиту ветки); данных и ключей у пользователя раннера нет.

## Тесты перед выкладкой (решение владельца 2026-10-22)
Тесты (`tests.yml`, вызывается из `deploy.yml`) идут на машинах GitHub (`ubuntu-latest`): Python 3.12 как на сервере, `pip install -e ".[dev]"`, `pytest tests -q --tb=short -n auto`. Для публичного репозитория минуты бесплатны; своих раннеров (Мак, сервер) у него нет. Задача одна и называется `pytest`, поэтому проверка — `tests / pytest` (её ждут `tires-pull` и защита `master`); имя задачи не менять, иначе опрос перестанет выкладывать (или задать новое имя в `TIRES_PULL_CHECK`). Частный документ Apps Script и схемы XML поставщика в публичной копии не лежат: их тесты пропускаются (с `TIRES_REQUIRE_PRIVATE_DOCS=1` — падают, для копии, где они должны быть). `pull_request` и `pull_request_target` в `tests.yml` не добавлять.

## Как GitHub достанет до сервера
| Вариант | Что открыть | Риск | Вывод |
|---|---|---|---|
| **Раннер на сервере (self-hosted runner)** | ничего: раннер сам ходит на github.com по HTTPS | раннер исполняет workflow из этого репозитория; поэтому у него свой пользователь без доступа к данным и ключам, sudo только на `tires-deploy`, выкладывается только последний master | **рекомендую** |
| Туннель (Tailscale в Actions) + SSH | ключ Tailscale и SSH-ключ в секретах GitHub | утечка секретов даёт сетевой доступ к серверу; ключ надо ограничивать `command=` | запасной |
| Прямой SSH из GitHub | порт 22 в интернет для всех адресов GitHub (их тысячи) | сервер открыт наружу | не рекомендую |

С раннером секретов в GitHub нет вовсе. Единственный ключ: **deploy key только на чтение** на сервере, им root забирает код.

## Что сделать владельцу (один раз)
**В GitHub (Settings репозитория):**
1. Репозиторий остаётся **приватным** (раннер на сервере нельзя подключать к публичному).
2. Actions → Runners → **New self-hosted runner**, Linux x64. Со страницы нужны две вещи: ссылка из строки `curl -o actions-runner-... -L <ссылка>` и токен из строки `./config.sh ... --token <токен>` (живёт час).
3. Rules (или Branches) → правило для **`master`**: запрет force-push и удаления, обязательная проверка `tests / pytest`. Обязательный PR не включать: Claude вливает `--ff-only` коммит, который уже прошёл тесты на своей ветке.

**На сервере (терминал, один раз):**
4. С компьютера, где есть доступ `tires-server`, из свежего master:
   `ssh tires-server mkdir -p /root/tires-setup`
   `scp deploy/setup-server.sh deploy/tires-deploy.sh deploy/sudoers-tires-deploy tires-server:/root/tires-setup/`
   `ssh -t tires-server bash /root/tires-setup/setup-server.sh '<ссылка из шага 2>' '<токен из шага 2>'`
   Скрипт заводит пользователя `tires-deploy` (без доступа к данным и ключам), ставит `tires-deploy` и правило sudo, создаёт ключ только на чтение и **попросит добавить его** в Settings → Deploy keys (без «Allow write access»), клонирует репозиторий в `/opt/tires-sync/repo`, ставит и запускает раннер с меткой `tires-prod`. Повторный запуск безопасен.

**Включить:**
5. На сервере `touch /etc/tires-deploy/enabled`; в GitHub Settings → Secrets and variables → Actions → Variables → `AUTO_DEPLOY_ENABLED` = `true`. Выключить быстро: `rm /etc/tires-deploy/enabled`.
6. Дальше выкладки идут сами при каждом push в master. Журнал: Actions → deploy; на сервере `/var/log/tires-deploy.log` и `/usr/local/sbin/tires-deploy status`.

## Коды выхода `tires-deploy`
0 чисто; 1 не начато (нет копии базы, не последний master, не дождался тишины, прочие ошибки до замены кода, включая ненулевые коды git); 2 панель не прошла проверку, код возвращён; 3 возврат не помог, нужен человек; 4 код выложен, `feed-check` нашёл ошибки.

## Выкладка опросом (tires-pull), без раннера на сервере
Зачем: перед тем как репозиторий станет публичным, раннер GitHub на боевом сервере надо убрать (этап 3 `docs/plans/2026-10-24-open-repo.md`): у публичного репозитория его быть не должно. Опрос сам ходит на GitHub только читать; GitHub до сервера не достаёт вовсе.

**Как работает.** Таймер `tires-pull.timer` раз в 2 минуты запускает `tires-pull.service` от пользователя `tires-pull` (у него нет доступа к базе и ключам; выложенный код, как и раньше, читать может любой пользователь сервера). Скрипт `/usr/local/sbin/tires-pull` (копия `deploy/tires-pull.sh`) спрашивает у GitHub последний коммит `master`. Если коммит не выложен, у него зелёная проверка `tests / pytest` от `github-actions`, он потомок выложенного и раньше не выкладывался, скрипт вызывает `sudo -n /usr/local/sbin/tires-deploy deploy <коммит>`. Всё остальное (замок, ожидание тишины, копия базы, проверка панели, возврат, таймеры, `feed-check`) делает `tires-deploy`, как при раннере. Каждый прогон пишет одну строку: `journalctl -u tires-pull -n 30`. Вывод последней выкладки: `/var/lib/tires-pull/last-deploy.log` и, как раньше, `/var/log/tires-deploy.log`.
- **Не выкладывается никогда:** коммит с красными, идущими или отменёнными тестами, без проверки или с проверкой от другого приложения; не потомок выложенного (тревога); коммит, у которого уже есть выпуск в `/opt/tires-sync/releases`, а выложен другой (был откат или выкладка не прошла; раннер такой не выкладывал, потому что срабатывал только на push, а опрос вернул бы откатанный коммит через 2 минуты); **после отката — ничего**, пока владелец не выложит вручную (любой коммит поверх откатанного, будь то следующая влитая ветка или запись в `docs/`, несёт то же плохое изменение, и по коммиту не понять, убрано ли оно; тревога один раз; `sudo /usr/local/sbin/tires-deploy deploy <коммит>` от root снимает паузу); если выпуски не прочитать или среди них нет выложенного (тогда правило отката не проверить, тревога). Без файла `/etc/tires-deploy/enabled` служба не запускается (тот же выключатель, что у раннера).
- **Повторы и тревоги** (тревога в Telegram через `tires-alert@`, на одно событие одна): `tires-deploy` не начал выкладку (код 1: замок, тишина, копия базы, отказ sudo; и любой непонятный код) — повтор через 10, 30, 60 минут, после 4-й неудачи коммит блокируется и приходит тревога (попытка записывается до вызова: не записалась — выкладка не вызывается, тревога); панель не прошла (2/3) — блокировка и тревога; `feed-check` или таймер (4/5) — тревога, код уже выложен. GitHub недоступен — ничего не делает, тревога после 30 сбоев подряд (около часа). `master` не выложен 3 часа по любой тихой причине (тесты стоят в очереди, Мак выключен, замок выкладки занят) — одна тревога на коммит. Заблокированный коммит больше сам не выкладывается: следующий коммит в `master` выкладывается как обычно. Снять блокировку вручную: удалить строку коммита из `/var/lib/tires-pull/blocked`.
- **Токен.** Пока репозиторий приватный, нужен токен только на чтение. Он лежит в `/etc/credstore/tires-pull.github-token` (root, 0600), а systemd отдаёт его службе (`ImportCredential`). В репозитории, журнале, окружении и аргументах команд его нет. У публичного репозитория без токена можно (удалить файл: в спокойном состоянии 30 запросов в час при лимите 60, тесты невыложенного коммита спрашиваются раз в 5 минут), но **лучше оставить токен**: fine-grained «Public repositories (read-only)» без прав даёт 5000 запросов в час, и выкладка не встанет из-за лимита.
- `tires-deploy` не ставит новые таймеры (выкладка трогает только те `deploy/*.timer`, что уже стоят на сервере; тест `tests/test_deploy_timers.py`), поэтому сам по себе `tires-pull.timer` не включится. Скрипт и службу выкладка тоже не ставит. После ручной установки файл таймера обновляется выкладкой, как остальные. sudo пропускает `tires-pull` только с `deploy <40 знаков hex>` (`deploy/sudoers-tires-pull`), а сам `tires-deploy` берёт из аргументов только второй и отвергает всё, кроме 40 знаков hex, до любых действий (тест `tests/test_deploy_timers.py`). Флаг `/etc/tires-deploy/enabled` для `tires-pull` проверяет systemd (`ConditionPathExists`), а не `tires-deploy` (тот проверяет его только для раннера).
- **Подделать зелёные тесты** может только workflow этого репозитория с правом `checks: write`. Поэтому в GitHub → Settings → Actions → General → Workflow permissions должно стоять **Read repository contents** (только чтение); наши workflow сами просят только `contents: read`.

**Установка (владелец, один раз; сначала на нынешнем приватном репозитории, раннер не трогаем).**
1. GitHub → Settings (своего профиля) → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate. Repository access: только `tires-avito-sync`. Permissions: **Contents: Read-only**, **Checks: Read-only** (Metadata подставится сам). Срок — до года, поставить напоминание о продлении.
2. С компьютера с доступом `tires-server`, из свежего `master`:
   `scp deploy/tires-pull.sh deploy/tires-pull.service deploy/tires-pull.timer deploy/sudoers-tires-pull tires-server:/root/tires-setup/`
3. На сервере (`ssh -t tires-server`, от root, в оболочке bash — у root на сервере она по умолчанию):
   ```
   cd /root/tires-setup
   useradd --system --no-create-home --shell /usr/sbin/nologin tires-pull
   install -o root -g root -m 0755 tires-pull.sh /usr/local/sbin/tires-pull
   visudo -cf sudoers-tires-pull && install -o root -g root -m 0440 sudoers-tires-pull /etc/sudoers.d/tires-pull
   install -d -o root -g root -m 0700 /etc/credstore
   ( umask 077; read -rsp 'токен: ' t; printf '%s\n' "$t" > /etc/credstore/tires-pull.github-token; unset t; echo )
   install -o root -g root -m 0644 tires-pull.service tires-pull.timer /etc/systemd/system/
   systemctl daemon-reload
   ```
   Токен вставить в приглашение `токен:` (на экране его не видно, в историю команд он не попадёт).
4. Проверка до включения:
   - `sudo -l -U tires-pull` — одно правило `tires-deploy ^deploy [0-9a-f]{40}$`;
   - `sudo -l -U tires-pull /usr/local/sbin/tires-deploy deploy $(cat /opt/tires-sync/deploy-state/deployed-sha)` печатает команду (разрешено), а `sudo -l -U tires-pull /usr/local/sbin/tires-deploy rollback` — отказ;
   - `sudo -u tires-pull cat /etc/credstore/tires-pull.github-token` — отказ (токен виден только службе);
   - `systemctl start tires-pull.service; journalctl -u tires-pull -n 5` — строка «выложен <коммит>, нового нет» или «ждём …». **Внимание:** если в `master` есть невыложенный коммит с тестами, зелёными больше 20 минут, этот запуск по-настоящему выложит его на сервер. «ответ 404 (нет доступа…)» значит, что токен не дошёл или без прав.
5. Включить: `systemctl enable --now tires-pull.timer`; `systemctl list-timers tires-pull.timer`.

**Запасной вариант токена** (если `ImportCredential` не сработает — в журнале «ответ 404 (нет доступа…)» при наличии файла): `install -d -o root -g root -m 0700 /etc/tires-pull`, токен в `/etc/tires-pull/github-token` (`root:root 0600`: файл читает systemd от root), в службе (`systemctl edit tires-pull.service`) строка `LoadCredential=tires-pull.github-token:/etc/tires-pull/github-token`. Важно: с `LoadCredential` без файла служба не запускается (и шлёт тревогу каждые 2 минуты), поэтому удалять файл можно только вместе с этой строкой.

**Неделя вместе с раннером.** В службе стоит `TIRES_PULL_MIN_AGE_MIN=20`: опрос выкладывает коммит, только если тесты зелёные уже 20 минут. Раннер выкладывает сразу, поэтому обычно первым успевает он, а опрос видит «выложен, нового нет». Опрос — запасной путь, если раннер не сработал. Один коммит дважды не выкладывается: оба идут через `tires-deploy`, а он под одним замком (`/run/tires-deploy.lock`) сначала сверяет коммит с `master`, затем пишет «уже выложен» и выходит с кодом 0 (строки «коммит … уже выложен» в `cmd_deploy`). Пока замок занят чужой выкладкой, опрос не встаёт в очередь, а пропускает ход; учёт перед вызовом он перечитывает под этим замком, окно до замка самого `tires-deploy` — миллисекунды. Если раннер выкладывал дольше 10 минут (ждал тишины), задача, пришедшая второй, выйдет с кодом 1 «идёт другая выкладка» — ничего не сломано. Неделю смотреть `journalctl -u tires-pull --since -1d | grep -v 'нового нет'`.

**Выключить раннер (после недели, по слову владельца).**
1. GitHub → Settings → Variables → `AUTO_DEPLOY_ENABLED` = `false`. Задача deploy пропускается, а тесты на `master` идут по-прежнему: проверка `tests / pytest`, которую ждёт опрос, остаётся.
2. Задержку убрать: `systemctl edit tires-pull.service` → `[Service]` и `Environment=TIRES_PULL_MIN_AGE_MIN=0`; `systemctl daemon-reload`.
3. Раннер: `systemctl disable --now actions.runner.pasha9230-tires-avito-sync.tires-server.service`. Через неделю без замечаний: `cd /home/tires-deploy/actions-runner && ./svc.sh uninstall` (от root), `sudo -u tires-deploy ./config.sh remove --token <токен со страницы Runners>` (от root `config.sh` не запускается), удалить раннер в GitHub → Actions → Runners, `rm /etc/sudoers.d/tires-deploy`. Остаются и убираются отдельно: пользователь `tires-deploy` с папкой `/home/tires-deploy` (`userdel -r tires-deploy`), окружение `production` в GitHub → Settings → Environments, переменная `AUTO_DEPLOY_ENABLED`.
4. Кнопки отката в Actions больше нет. Откат теперь: `ssh tires-server sudo /usr/local/sbin/tires-deploy rollback`. После отката опрос сам ничего не выкладывает (пауза, одна тревога): Claude делает `git revert` плохого коммита в `master`, тесты зелёные, затем владелец один раз выкладывает вручную `ssh tires-server sudo /usr/local/sbin/tires-deploy deploy <коммит>` (только последний master) — это снимает паузу, дальше опрос работает как обычно.
5. Переезд на публичный репозиторий (этап 5): если меняется имя, `systemctl edit tires-pull.service` → `Environment=TIRES_PULL_REPO=<владелец>/<имя>`. Токен заменить на новый (fine-grained, «Public repositories (read-only)») или удалить файл; старый отозвать. Если тесты переедут в другой workflow, имя проверки задаётся в `TIRES_PULL_CHECK`.

**Откат опроса.** `systemctl disable --now tires-pull.timer` — опрос больше не запускается, раннер (пока он есть) выкладывает как раньше. Полностью убрать: `rm /etc/systemd/system/tires-pull.{service,timer} /usr/local/sbin/tires-pull /etc/sudoers.d/tires-pull /etc/credstore/tires-pull.github-token`, `systemctl daemon-reload`, `userdel tires-pull`, `rm -r /var/lib/tires-pull`, отозвать токен в GitHub. Код: `git revert` коммита. База и выложенный код при этом не трогаются.
